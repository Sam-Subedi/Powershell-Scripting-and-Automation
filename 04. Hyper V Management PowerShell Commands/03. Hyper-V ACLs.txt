# Enforce network segmentation from the Hyper-V host itself using built-in Hyper-V Extended ACLs (Access Control Lists)
This blocks or allows traffic at the virtual switch level before it even reaches the VM's network card, meaning you don't have to configure anything inside the VMs. It is usually preferred because it mimics how a real network firewall operates at the switch level. It runs on the physical host using PowerShell, providing higher security because traffic is blocked before entering the VM. Furthermore, it is tamper-proof because a user inside the VM cannot bypass it.

system administrators and security engineers prefer doing network segmentation at the hypervisor (host) level rather than inside the guest operating system:

True Isolation: The virtual switch drops malicious or unwanted traffic before it can even touch the virtual network interface card (vNIC) of the VM.

Tamper-Proof Security: Even if an attacker completely compromises your virtual machine and gains full Administrator or Root privileges inside the guest OS, they cannot change or bypass these rules. They are completely trapped by the networking rules you set up on your main physical PC.

Mimics Real Enterprise Networks: This matches how real data centers work, where network security is handled by physical top-of-rack switches or firewall appliances, completely independent of the servers themselves.

On the Host (Hyper-V Switch Layer): You run these commands in PowerShell on your physical host computer. This is true hypervisor-level segmentation.

Example: 
To block all inbound traffic from the VLAN 20 subnet (192.168.2.0/24) to your AD VM:
Add-VMNetworkAdapterAcl -VMName "Your AD VM" -RemoteIPAddress "192.168.2.0/24" -Direction Inbound -Action Deny

To allow only a specific IP from VLAN 20 (like a management PC at 192.168.2.50) to talk to the AD VM:
Add-VMNetworkAdapterAcl -VMName "Your AD VM" -RemoteIPAddress "192.168.2.50" -Direction Inbound -Action Allow

How to CHECK Your Current ACL Rules?
Get-VMNetworkAdapterExtendedAcl -VMName "VM Name"

If the output is completely blank, it means there are no custom firewall restrictions on that VM yet, and it is currently wide open to the virtual networks it connects to. To use Hyper-V Extended ACLs and check existing rules on your host PC, you will use two specific PowerShell commands: Add-VMNetworkAdapterExtendedAcl to create rules and Get-VMNetworkAdapterExtendedAcl to view them. Extended ACLs are stateful by default when you specify a direction, meaning if you allow traffic out, Hyper-V automatically tracks it and allows the response back in.

Using Extended ACLs (Examples):Extended ACLs are stateful by default when you specify a direction, meaning if you allow traffic out, Hyper-V automatically tracks it and allows the response back in. Here are the most common rules you will need for your Active Directory (VLAN 10) and Client (VLAN 20) setup:

Example A: Block the ENTIRE Client Subnet from your AD VM
This rule tells the Hyper-V switch to drop any traffic originating from the client network (192.168.2.0/24) heading toward your AD server.
Add-VMNetworkAdapterExtendedAcl -VMName "Your AD VM Name" 
    -RemoteIPAddress "192.168.2.0/24" 
    -Direction Inbound 
    -Action Deny 
    -Weight 10

Example B: Only Allow Active Directory Traffic (DNS & LDAP)
If you want your clients to be able to log in to the domain but block them from everything else, you create an "Allow" rule for specific ports. You must give this a higher Weight number so it overrides the Deny rule above. Allow DNS requests (Port 53 TCP/UDP):
Add-VMNetworkAdapterExtendedAcl -VMName "Your AD VM Name" 
    -RemoteIPAddress "192.168.2.0/24" 
    -Protocol TCP 
    -LocalPort 53 
    -Direction Inbound 
    -Action Allow 
    -Weight 20

Example C: How to REMOVE a Rule if You Make a Mistake?
If a rule breaks your lab setup, you can remove it easily. Simply change the word Add at the start of your command to Remove, keeping all other parameters exactly the same:
Remove-VMNetworkAdapterExtendedAcl -VMName "Your AD VM Name" 
    -RemoteIPAddress "192.168.2.0/24" 
    -Direction Inbound 
    -Action Deny 
    -Weight 10 

Example D:How to Read the Output?
If the command returns absolutely nothing (blank screen): It means you have no ACL rules active on your host PC. Your virtual network is completely open, and traffic is flowing freely based on standard routing.

If rules exist: You will see a list showing columns like RemoteIPAddress, Direction (Inbound/Outbound), Action (Allow/Deny), and Weight.

# Enforce network segmentation Inside the VM (Guest OS Firewall Layer)

Inside the VM (Guest OS Firewall Layer):You log into the Guest VM (like your Active Directory server) and run these commands in its local PowerShell window. To create a rule blocking the entire VLAN 20 client subnet:
New-NetFirewallRule -DisplayName "Block VLAN 20 Subnet" 
    -Direction Inbound 
    -Action Block 
    -RemoteAddress 192.168.2.0/24


# How to Use Hyper-V Firewall Rules?
Microsoft provides dedicated NetSecurity commands explicitly designed to leverage these APIs. To use them, open an Administrative PowerShell prompt on your Hyper-V host. 

1. Create a Rule to Block Specific Traffic to a VM
If you want to block a specific port (e.g., blocking standard HTTP port 80) to a targeted virtual machine, use the New-NetFirewallHyperVRule cmdlet.

Example: New-NetFirewallHyperVRule -DisplayName "Block HTTP to WebVM" 
                          -Direction Inbound 
                          -Action Block 
                          -Protocol TCP 
                          -LocalPort 80

2. Create a Rule to Allow Traffic Only from a Specific IP
If you want to isolate a sensitive VM network card so that it only accepts administrative traffic (like RDP on port 3389) from a specific management subnet:

Example: New-NetFirewallHyperVRule -DisplayName "Allow Admin RDP Only" 
                          -Direction Inbound 
                          -Action Allow 
                          -Protocol TCP 
                          -LocalPort 3389 
                          -RemoteAddress "192.168.10.0/24"

3. Create a Rule to Allow Traffic Only from a Specific IP
   To block your endpoint client subnet (VLAN 20) from accessing a specific sensitive port (like RDP) on your AD subnet (VLAN 10):
   Example: New-NetFirewallRule -DisplayName "Block VLAN 20 RDP to VLAN 10" 
                           -Direction Inbound 
                           -Action Block 
                           -Protocol TCP 
                           -LocalPort 3389 
                           -RemoteAddress 192.168.2.0/24
                   

4. View All Active Hyper-V Switch Rules
To audit what rules are currently running natively at the Hyper-V switch layer, run: Get-NetFirewallHyperVRule

When should you use this instead of a normal firewall?

Container Isolation: It is heavily used automatically by Windows to isolate network traffic for Windows Subsystem for Linux (WSL) and Docker/Windows Containers.

Hypervisor-Level Enforcement: It stops malicious network traffic at the virtual switch level, saving the VM's CPU from processing bad packets.

Immutable Security: Because the rule is enforced by the Hyper-V host, a user or hacker who gains Administrator rights inside the Virtual Machine still 
cannot bypass or disable the firewall rule.

5. Filter Directly on the Virtual Machines: Instead of filtering traffic in the middle of the network, you can let Windows route the traffic freely and use  PowerShell to configure the local Windows Firewall inside the VMs themselves.

Example PowerShell Command (Run inside your VM): New-NetFirewallRule -DisplayName "Allow VLAN 20 Clients to AD" 
    -Direction Inbound 
    -Action Allow 
    -RemoteAddress 192.168.2.0/24 
    -Enabled True

* You must run these commands on your Hyper-V host inside an Administrative PowerShell window to bind rules to a specific virtual machine's name or to completely block a VM from talking to other VMs on the same switch.

Script 1: Bind a Hyper-V Firewall Rule to a Specific VM
By default, standard HyperVRule commands apply globally to the virtual switches. To target a specific virtual machine, you must retrieve its internal Network Adapter ID (Port ID) and bind the rule directly to it using the -VMSwitchPortIds parameter.This script targets a specific VM (e.g., "ProductionSQL") and blocks inbound SSH traffic (Port 22) before it even reaches the VM's OS:

# 1. Get the unique internal Switch Port ID of your target VM
$VMPort = (Get-VMNetworkAdapter -VMName "ProductionSQL").Status.VMId

# 2. Create the Hyper-V firewall rule specifically bound to that port
New-NetFirewallHyperVRule -DisplayName "Block SSH to ProductionSQL" 
                          -Direction Inbound 
                          -Action Block 
                          -Protocol TCP 
                          -LocalPort 22 
                          -VMSwitchPortIds $VMPort

Script 2: Isolate a VM (Block it from talking to other VMs on the same switch)
If you want to isolate a VM so it can talk to the internet/gateway but cannot probe, hack, or communicate with neighbor VMs on the exact same virtual network, you use VM Network Adapter Extended ACLs.This method creates an isolation boundary directly inside the virtual switch layer:

# 1. Block ALL outbound traffic from this VM to the local subnet (e.g., 192.168.1.0/24)
Add-VMNetworkAdapterExtendedAcl -VMName "IsolatedVM" 
                                -Direction Outbound 
                                -Action Deny 
                                -LocalMacAddress $null 
                                -RemoteMacAddress $null 
                                -RemoteIpAddress "192.168.1.0/24" 
                                -Weight 10

# 2. Allow the VM to talk exclusively to your default gateway/router (e.g., 192.168.1.1)
# (This ensures it can still get out to the Internet, but can't touch neighbor VMs)
Add-VMNetworkAdapterExtendedAcl -VMName "IsolatedVM" 
                                -Direction Outbound 
                                -Action Allow 
                                -LocalMacAddress $null 
                                -RemoteMacAddress $null 
                                -RemoteIpAddress "192.168.1.1" 
                                -Weight 20

Note: The Weight parameter tells Hyper-V which rule to process first. The higher weight (20) overrides the lower weight (10), allowing the gateway traffic through while blocking everything else.

Script 3: How to clear or reset these rules if you make a mistake?
If you ever need to completely remove these rules and restore standard communications, use these quick reset commands:

# To remove the Hyper-V Firewall port rule:
Remove-NetFirewallHyperVRule -DisplayName "Block SSH to ProductionSQL"

# To clear all isolation rules from a VM:
Remove-VMNetworkAdapterExtendedAcl -VMName "IsolatedVM"

Script 4: Check Existing ACL Rules on a VM
Before adding new rules, it is best practice to see what blocks or allowances are already configured on a virtual machine. This command dumps every Extended Access Control List (ACL) attached to a specific network adapter:

# View all custom network security filters applied to a specific VM
Get-VMNetworkAdapterExtendedAcl -VMName "IsolatedVM" | Select-Object Direction, Action, RemoteIpAddress, Weight

Note: If this returns absolutely nothing, it means the virtual switch is running wide open with default configurations (no rules applied).

Script 5: Build a DMZ Rule (Talk ONLY to one specific server)
If you have a front-end web server or a DMZ machine that should only be allowed to talk to a single backend database server (and absolutely nothing else on your local network), you use a layered approach using weights.This example allows a VM named "WebServer" to communicate exclusively with a Database Server at 192.168.1.50, while completely blocking it from the rest of your local private network (192.168.1.0/24):

# 1. ALLOW traffic to and from the specific database server (Highest priority: Weight 30)
Add-VMNetworkAdapterExtendedAcl -VMName "WebServer" -Direction Both -Action Allow -RemoteIpAddress "192.168.1.50" -Weight 30

# 2. ALLOW traffic to the gateway/router so it can access the Internet (Weight 20)
Add-VMNetworkAdapterExtendedAcl -VMName "WebServer" -Direction Both -Action Allow -RemoteIpAddress "192.168.1.1" -Weight 20

# 3. DENY all other traffic to the entire local network subnet (Lowest priority: Weight 10)
Add-VMNetworkAdapterExtendedAcl -VMName "WebServer" -Direction Both -Action Deny -RemoteIpAddress "192.168.1.0/24" -Weight 10

How the Layered Rules Work?
Hyper-V processes rules starting from the highest weight down to the lowest. If the VM tries to talk to 192.168.1.50, it hits the first rule (Weight 30) and is Allowed. If it tries to talk to 192.168.1.1 (the internet gateway), it bypasses the first rule, hits the second rule (Weight 20), and is Allowed. If it tries to scan or attack a random neighbor machine like 192.168.1.155, it falls through to the final rule (Weight 10) and is Denied.


* How to adapt these rules to filter traffic by MAC Addresses instead of IP addresses?
To filter virtual machine traffic by MAC addresses instead of IP addresses, you use the exact same Add-VMNetworkAdapterExtendedAcl cmdlet. However, you leave the -RemoteIpAddress blank and use the -RemoteMacAddress parameter instead. Filtering by MAC address is highly secure because it operates at Layer 2 (Data Link Layer). This means even if a VM changes its IP address inside the guest OS, the virtual switch will still block or allow traffic based on the hardcoded hardware identity of the target machine.

Step 1: Find the MAC Address of the Target Computer
Get-VMNetworkAdapter -VMName "TargetVMName" | Select-Object VMName, MacAddress
Format Note: Hyper-V requires MAC addresses to be formatted as 12 continuous hex characters without dashes or colons (e.g., 00155D010A12)

Step 2: Apply MAC-Based Firewall Rules

Scenario A: Create a "Mac Whitelist" (Block all neighbors except one specific server)
If you want a VM named "SecureVM" to communicate only with a specific physical backup server or appliance on your network, while completely cutting off communication to all other network cards:

# 1. ALLOW traffic to the specific trusted MAC address (Higher Priority)
Add-VMNetworkAdapterExtendedAcl -VMName "SecureVM" 
                                -Direction Both 
                                -Action Allow 
                                -RemoteMacAddress "00155D010A12" 
                                -Weight 20

# 2. DENY traffic to every other MAC address on the network (Lower Priority)
# (The asterisk "*" acts as a wildcard for all MAC addresses)
Add-VMNetworkAdapterExtendedAcl -VMName "SecureVM" 
                                -Direction Both 
                                -Action Deny 
                                -RemoteMacAddress "*" 
                                -Weight 10


Scenario B: Block a Specific Malicious or Rogue Device If you suspect a specific machine or virtual appliance on your network is compromised, you can hard-block your VM from interacting with it entirely:

Add-VMNetworkAdapterExtendedAcl -VMName "SecureVM" 
                                -Direction Both 
                                -Action Deny 
                                -RemoteMacAddress "0025B3A19C4F" 
                                -Weight 50

How to Check and Remove MAC Rules?
To verify that your MAC filters are properly attached to the network adapter, run:
Get-VMNetworkAdapterExtendedAcl -VMName "SecureVM" | Select-Object Direction, Action, RemoteMacAddress, Weight

If you need to completely clear a MAC-based rule later, use:
Remove-VMNetworkAdapterExtendedAcl -VMName "SecureVM" -Direction Both -Action Deny -RemoteMacAddress "*"

* How Hyper-V Port Mirroring works to capture and analyze this network traffic?

Hyper-V Port Mirroring allows you to copy all the network traffic entering or leaving a specific virtual machine and stream it to a second monitoring virtual machine. This is incredibly useful for network troubleshooting, security auditing, or feeding network data into an intrusion detection system (IDS) or packet sniffer (like Wireshark). Because this happens at the hypervisor layer, the target VM has no idea its traffic is being duplicated. Configuring Hyper-V Port Mirroring is a two-step process: you must configure one VM as the Source (the machine you want to spy on) and another VM as the Destination (the machine running Wireshark/IDS).

Step 1: Configure the Source VM (The Machine Being Monitored)
You tell the virtual switch to copy this VM's traffic. Run this in an Administrative PowerShell window on your Hyper-V host:

# Set the VM network adapter to send a copy of all its traffic
Set-VMNetworkAdapter -VMName "ProductionWebServer" -PortMirroring Source


Step 2: Configure the Destination VM (The Monitoring Machine)
You tell the virtual switch to deliver the copied traffic to this specific machine's network card.

# Set the monitoring VM network adapter to receive the copied traffic
Set-VMNetworkAdapter -VMName "WiresharkMonitoringVM" -PortMirroring Destination

Step 3: Configure the Guest OS to capture the traffic
Once the Hyper-V switch is mirroring the ports, log into your Destination VM (e.g., WiresharkMonitoringVM):
Open Wireshark (or your preferred packet capture tool).
Start a capture on the network interface connected to that virtual switch.
You will immediately begin seeing packets belonging to IP addresses that do not match your monitoring VM.

How to Turn Off Port Mirroring?
 When you are finished troubleshooting or monitoring, you should turn port mirroring off to save hypervisor CPU and network overhead. Run these commands to reset the adapters back to normal:

# Reset both VMs back to default network behavior
Set-VMNetworkAdapter -VMName "ProductionWebServer" -PortMirroring None
Set-VMNetworkAdapter -VMName "WiresharkMonitoringVM" -PortMirroring None

Crucial Requirement: The Same Virtual SwitchFor basic Hyper-V port mirroring to work, both virtual machines must be connected to the exact same Virtual Switch on the same physical host. If your VMs are on different cluster nodes or different switches, standard mirroring won't bridge across them without advanced Microsoft Software-Defined Networking (SDN) configurations.
